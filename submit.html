收录说明

只要你做的 DFC 附属 mod 有公开仓库、有挂 jar 的 Release，就能加到这里。 提交一次，之后版本更新全自动同步，不需要反复找我。

  • 支持 Gitee / GitHub
  • 整点自动同步
  • 署名保留在你自己仓库

怎么提交

把这三样发给我就行，不用写文档：

  1. 仓库地址（Gitee 或 GitHub 都行，公开仓库）；
  2. 模组名字和一句话介绍；
  3. 作者署名想怎么写。

发到 B 站私信最快：space.bilibili.com/3494363348863838。 不想私信的话，在本站的 GitHub 仓库提个 issue 也一样。

收录条件

项要求
仓库公开可读，Gitee / GitHub 均可
Release至少一个发行版，且把 .jar 作为附件挂在发行版上（不要只推源码）
许可证仓库里有 LICENSE 文件。本站直接读它显示，不做二次判断
署名如果用了别人的代码，请在 README 里写清来源
内容与 DFC 地图 / 特效工具相关，或者同属 HBM-DFC 圈

源码包、-sources.jar、-javadoc.jar 会被自动过滤，不显示成可下载文件。

收录之后

站点每小时跑一次同步，直接从你的仓库读这些内容，都不需要手动改：

  • 版本列表：发行版的 Tag、标题、更新时间、附件、更新说明；
  • 通道与性质标签：按下面第三节的规则从 Tag / 标题 / 说明里识别；
  • 参数表：开源许可读仓库的 LICENSE，游戏版本与加载器默认 1.12.2 / Forge 14.23.5.2864；
  • 下载次数：GitHub 会给出每个附件的下载数，Gitee 接口没有这个字段，那边显示「不提供」。

「需要 JiezhiMod 作为前置」这一行默认是「否」。真的需要本体时告诉我，我会改成「是」。

通道标签：正式版 / 测试版 / 预览版

看 Tag 的后缀，没有后缀就是正式版。

你写的 Tag站点认成
v3.9、3.9、v3.9-release正式版
v3.9-beta、v3.9-beta.2测试版
v3.9-preview、-alpha、-rc1、-snapshot预览版
Tag 没后缀，但标题以「测试版 / beta」结尾测试版
Tag 没后缀，但在 GitHub 勾了 Pre-release预览版

顺序是：先看 Tag 后缀 → 再看标题末尾 → 最后看 Pre-release 勾选。所以 v3.9.1 + 标题「v3.9.1 测试版」会算测试版。

紧急修复 / 重大更新

这两个是叠加标签，不影响通道，可以和正式版、测试版同时出现。

紧急修复

适合「刚发出去就发现严重 bug，得马上补一个」的版本。下面任意一条命中就算：

  • Tag 里有 hotfix / hot-fix / urgentfix / emergencyfix，或者以 -fix 结尾； 例：v3.9.1-hotfix、v3.9.1-hotfix-beta、v3.9.1-fix
  • 标题里出现「紧急修复」或 hotfix；例：v3.9.1 紧急修复版 + 测试版
  • 说明的前 200 字里出现「紧急修复版」或 hotfix

普通更新日志里写「修复了几个崩溃」不会被认成紧急修复 —— 只认「紧急修复版」这种明确说法。

重大更新

只给正式版用。测试版 / 预览版即使写了「重大更新」也不会打这个标签。

  • Tag 里有 major；例：v3.10-major
  • 标题里有「重大更新」或 major；例：v3.10 重大更新
  • 说明的前 200 字里有「重大更新」

v3.10-major-beta 会被认成「测试版」，不带重大更新 —— 这是故意的：转正之前不算重大更新。

想同时要两个

直接组合就行：v3.9.2-hotfix-major 会同时带上「紧急修复」和「重大更新」（前提是它是正式版）。 更常见的做法是 Tag 写干净，在标题里描述，比如 v3.9.2 紧急修复：密码盘错位。
